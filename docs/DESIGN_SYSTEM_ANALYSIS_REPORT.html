SOPilot · Config Management · Design

System Analysis Report → Stage-1 Schema

Status: proposal (not built) · companion to the Config-Schema (DSL) design · source: NEW_FEATURES.md “Enhanced System Analysis”

An automated Stage-0 analysis produces a structured JSON report of a target system — its components, every possible configuration item, integration points, and dependencies, including what is still unknown. That report becomes the authoritative seed for the Stage-1 schema the admin curates. This document defines the report’s shape and how it flows through the configurator.

1 · Where this sits

Stage 0
Analysis → a structured JSON report of the system (components, all config items, integrations, dependencies, and the unknowns). Produced offline by experts + Claude; input may be a sample config, a DB schema, or source code.
▼
Stage 1
Schema — the admin curates a ConfigSchema (the DSL) seeded from the report; declares rules (bounds).
▼
Stage 2
Config — the user authors a config within schema + rules, then write-back renders a validated deploy artifact.

Today Stage 1 is seeded from a sample config, which only reveals fields present in one example. The Analysis report replaces that weak seed with an authoritative one: it names all config items with types, enums, defaults, requiredness, dependencies — and the items that are needs_input and await Engineering.

The configurator only ever consumes the report, never the raw system. The report is the normalized output of analysis whose input may be a sample config, a database schema, or code — a clean boundary that keeps the configurator source-agnostic (handles “the DB schema itself is the data source”).

2 · The report JSON (the keystone)

{
  "kind": "sopilot-system-analysis",
  "report_version": 1,
  "system": {
    "name": "polartie-voice-robot",
    "description": "...",
    "analyzed_at": "2026-07-25T…",           // stamped by the analysis run
    "sources": ["sample_config", "db_schema"] // what analysis drew on
  },

  // Architecture — renders as a dependency diagram (reuses ConfigGraph).
  "components": [
    { "id": "voice_agent", "name": "Voice Agent", "kind": "service",
      "description": "...", "depends_on": ["knowledge_mcp", "schedule_mcp"] },
    { "id": "knowledge_mcp", "name": "Airport Knowledge MCP", "kind": "external",
      "description": "Context Graph", "depends_on": [] }
  ],

  // The config surface → becomes ConfigSchema fields / tools / structures.
  "config_items": [
    { "path": "voice", "item": "field", "type": "enum",
      "options": ["alloy","echo","coral"], "required": false,
      "description": "TTS voice", "component": "voice_agent",
      "status": "known", "source": "sample_config" },

    { "path": "weather_provider", "item": "field", "type": "enum",
      "options": [], "required": true, "description": "live weather source",
      "component": "voice_agent",
      "status": "needs_input", "source": "code" },          // options unknown

    { "path": "send_email", "item": "tool", "description": "send an email",
      "status": "known", "source": "code" },

    { "path": "mcp_servers", "item": "structure", "description": "MCP endpoints",
      "status": "known", "source": "sample_config" }
  ],

  // Retrieval / external systems → connectors + structure entries.
  "integration_points": [
    { "name": "airport-facts", "kind": "rag",
      "source_ref": "postgres:aena.documents",   // db-as-source example
      "auth": "secret-ref", "description": "...", "component": "knowledge_mcp" }
  ],

  // The feedback loop: what analysis could NOT resolve → to Engineering.
  "open_questions": [
    { "about": "weather_provider", "question": "what are the allowed providers?",
      "needs_from": "engineering" }
  ]
}

Field notes

  • status known needs_input inferred — the known-vs-unknown notion. needs_input items appear in the schema but are flagged (Stage 2 can’t finalize them; write-back warns) until Engineering supplies the missing facts.
  • source per item records provenance (sample config / db schema / code / manual) — audit + merge decisions.
  • item (field | tool | structure) maps 1:1 to the three parts of ConfigSchema.
  • depends_on on components (and optionally items) drives the diagram and later cross-field rules.

3 · Importer: report → schema

A new importer beside the existing schemaFromConfig:

schemaFromAnalysisReport(report): ConfigSchema
  fields:     config_items where item==="field"     (type, options, required, description, advanced)
  tools:      config_items where item==="tool"      (name=path, description)
  structures: config_items where item==="structure" (key=path)

needs_input items carry through as a field flag so the admin sees “declared but awaiting Engineering.” Everything the admin then edits layers on top — the same curate-then-publish flow that exists now.

4 · Re-analysis: versioned, DB-stored, merge-not-clobber

All configs are DB-stored and versioned, and the report is one of those artifacts. Analysis runs after each major system update or at onboarding, so each run is a new immutable version:

  • ConfigAnalysisReport / ConfigAnalysisReportVersion (SopVersion-style: immutable versions, a published_version pointer, per tenant/project), mirroring ConfigRuleset. GET/PUT /config/analysis + history.
  • Sync-to-schema is explicit and merges — re-import must not wipe curation. Merge rule (by path):
    • the report is authoritative for existence, type, dependencies, source, status (structural facts);
    • the admin is authoritative for label, description overrides, required, advanced, curated enum options once a field is touched;
    • added items appear flagged “new”; removed items are flagged gone in vN (never silently dropped).
    Provenance (source + an “admin-touched” bit) is what keeps the merge honest.

Full artifact set per project, all versioned in the DB:

describes
Analysis report (Stage 0)
▼
types
Schema (Stage 1) · Ruleset (bounds)
▼
is
Config document → rendered robot config

The DB-versioning stage should stand all of these up on the one proven ConfigRuleset pattern.

5 · Diagram view

components + depends_on + integration_points render with the existing ConfigGraph machinery — the “better in diagram form” ask, at low cost. For example:

Voice Agent
service · depends on ↓
Airport Knowledge MCP
external · Context Graph
Schedule MCP
external · flight status

Read-only; the analysis itself needs no authoring UI (offline expert + Claude process producing the JSON).

6 · The feedback loop to Engineering

  • Analysis → Admin: unresolved items arrive flagged needs_input; the admin can’t finalize them.
  • Admin → Engineering: when the admin needs an option the schema lacks (already surfaced when the guided-edit assistant hits an out-of-vocab request), that becomes an open_question exported for the next analysis round.
