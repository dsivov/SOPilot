The SOPilot Configuration Engine

How to take a robot from an unknown system to a safe, deployable configuration — Stage 0 discovery, through Stage 1 admin guard-rails, to a Stage 2 customer-authored config — and how all of that lives alongside SOP management. Written from the shipped code, not the design proposals.

The idea

What this is

The configuration engine is a constraint-graph over your robot's config surface. Instead of hand-editing a fragile config.json, the work is split into three roles, each producing one durable, versioned artifact.

Stage 0 · Discovery

Analyze a system and emit a machine-readable analysis report: what can be configured, what's unknown, and how the pieces connect.

Stage 1 · Bounds (admin)

Turn that report into a schema (the available options, typed) plus rules (what combinations are legal). The guard rail.

Stage 2 · Configure (customer)

Author the actual config document, guided and gated by the published schema + rules — impossible-to-deploy states are blocked before they happen.

A final write-back step resolves connector and secret references into the deploy-ready config.json the robot consumes.

◆ The core principle
The admin defines the space of valid configurations once; every customer then configures within that space. The engine — not a human reviewer — enforces the boundary on every edit.
Orientation

The big picture

The four steps form a pipeline. Each stage hands a versioned artifact to the next; the roles (who does the work) are distinct.

Three artifacts, all versioned in the database

Per tenant × project, the engine stores three independent artifacts in Postgres. Each is an immutable version history with a single published_version pointer — the published version is the only one anything downstream reads. Everything survives an API restart or redeploy; the browser holds only a draft cache.

StageArtifactTablesEndpoint
0Analysis reportconfig_analysis_reports (+ versions)/config/analysis
1Schema + rulesconfig_rulesets (+ versions)/config/ruleset
2Config documentconfig_documents (+ versions)/config/document
◆ Restart-survival, proven
You can verify persistence end-to-end: run scripts/e2e_config_manager.py (writes all three stages), restart the API, then re-run with --verify-only. Both runs end with ALL CHECKS PASSED. See §09.
Vocabulary

Key concepts

A short glossary — every term below appears in the Studio and the rest of this guide.

TermWhat it means
Schema (DSL)The admin's declaration of the available options: fields (with types), the tool allowlist, and which structures are offered. This is what Stage 2 renders as widgets.
RuleA constraint authored as data — one of three kinds: enum (a field must be one of N options), requires (if A then B), conflicts (not both A and B). Each is error or warn.
PredicateThe atom a rule tests: tool:<name> (tool enabled; | = any-of), field:<dot.path> (field set), kb_mode:<mode> (a knowledge base uses that index mode).
Field typestring · number · boolean · enum · secret-ref · connector-ref. The last two point at a stored secret or a registry connector rather than holding a value.
StatusOn a discovered item: known, inferred, or needs_input (declared but awaiting Engineering — shown with a ⚑ in Stage 2).
StructureA list-valued part of the config: mcp_servers, knowledge_base, transfer_topics.
ConnectorA connection (MCP / RAG / HTTP / DB) defined once in the registry and reused by both SOPs and the config editor. Referenced by name; resolved at write-back.
secret-refThe string secret:<name>. Raw credentials never enter a config or report — they live encrypted (Fernet) in tenant_secrets and resolve only at write-back.
Published versionThe one version of an artifact that downstream reads. Saving a draft creates a version but does not move the published pointer.
The boundary

SOP management ↔ Config management

SOPilot has two subsystems that live in the same instance and Studio. They answer different questions and are easy to confuse, so this section is deliberate about the boundary.

SOP management

“What should the agent do and say, turn by turn?”

Versioned procedures — actions, user-states, data dependencies, prompt blocks. Drives runtime guidance: per-turn steering, gated flows, live data resolution. Reaches the robot over the MCP supervisor at /mcp. Studio: SOPs · Prompt blocks.

Config management

“What is this robot — its capabilities and settings?”

Versioned configuration — persona, voice, tool allowlist, MCP servers, KBs, transfer topics, prompt. Authored within admin bounds; rendered to a deploy config.json. This document's Stage 0 → Stage 2. Studio: Config admin · Config viewer.

How they connect at runtime

They are not rivals — they compose. The config manager defines the robot's mcp_servers; one of those entries points at SOPilot's own MCP surface, which is how the robot consults its SOPs mid-call. The connector registry is shared: define a connection once, bind it in an SOP's data dependency and add it to a config via “+ from connector”.

Subsystem modes

A project runs in one of four modes. The default is both (deployment env SOPILOT_SUBSYSTEMS); it can be overridden per project (Studio topbar dropdown) and per session (most specific wins).

ModeSOPBackground retrievalUse when
both✔ gated per-turn contract✔ prediction + prefetchFull system — the default.
sop✔ instruction management + live data—Procedure guidance without speculative retrieval.
retrieval—✔ per-turn context_blockBring your own agent; take our context block into your prompt.
advisory✔ full SOP text in one calloff the reply pathLowest latency. AENA production runs advisory.
◆ SOP-only vs Advisory
SOP-only keeps the full per-turn contract (classification + tracking on the reply path) so the flow is gated step by step. Advisory hands the responder the full SOP text plus fresh data in one call and moves classification/tracking off the reply path — you trade fine-grained gating for the lowest possible latency.
Stage 0 · engineer / analyst

System Discovery

Stage 0 turns an unknown system into a machine-readable analysis report: what's configurable, what's still unknown, and how the components connect. It's a Claude-driven discovery run — not a deterministic parser — so it works whether the “source” is a codebase, a DB schema, or a sample config.

Producing a report — three ways

WayHow
Skill (recommended)Point Claude Code at the target (e.g. ../pt-multirobot) and invoke the system-analysis skill. It explores the code, writes docs/examples/<system>-analysis.json, validates it, and reports the path + summary.
Playbook (manual)Follow docs/STAGE0_ANALYSIS_PLAYBOOK.md — 7 steps: orient → find the config surface → map components → map connections → record unknowns → emit & validate → load.
Bootstrap demoDerive a throwaway report from a loaded config just to exercise the import flow (tools only) — not real analysis.

The report JSON — the contract

Top-level keys (see docs/examples/pt-multirobot-analysis.json for a full example):

KeyMeaning
kindMust equal "sopilot-system-analysis".
report_versionNumber (currently 1).
system{ name, description, analyzed_at, sources[] }. Sources: sample_config · code · db_schema · …
components[]Architecture nodes: { id, name, kind(service|external|datastore), depends_on[], exposes[] }. exposes[] = inbound endpoints the component serves.
config_items[]The config surface (see below) — this is what seeds the schema.
integration_points[]Outbound connections: { name, kind(db|http|webhook|mcp|rag), direction, technology, target, auth{secret_ref} }. Credentials are secret_ref only.
open_questions[]{ about, question, needs_from(engineering|admin) } — the unknowns to route back.

A single config_items[] entry maps 1:1 to a schema field / tool / structure:

// one entry in config_items[]
{
  "path": "custom_config.gpt_model",
  "item": "field",        // field | tool | structure → schema fields/tools/structures
  "type": "enum",         // string|number|boolean|enum|secret-ref|connector-ref
  "options": ["gpt-realtime", "gpt-4o-realtime"],
  "required": true,
  "status": "known",      // known | inferred | needs_input
  "description": "Realtime model the voice agent uses"
}
◆ enum needs options — unless it's unknown
An enum field must carry options, except when status: "needs_input" (then options: [] is allowed and Stage 2 renders it as a text input until Engineering fills it in).

Validate, then load

  1. Validate offline. python scripts/validate_analysis_report.py <report.json> → exit 0 prints ✔ valid + a summary (N fields · N tools · N structures · N integrations · N components); exit 1 lists the problems. It checks the kind, unique item:path keys, valid statuses/types, and enum-has-options-or-needs-input.
  2. Import in the Studio. Go to Config admin → the card “Available options — schema (DSL)” → “Import analysis report…” and pick the JSON.
  3. It persists and seeds. The report is saved as a version (PUT /config/analysis) and the schema is seeded from it. First import seeds fresh; a later import merges — the report is authoritative for existence/type/options/status, the admin keeps required/advanced/labels, and dropped fields are kept and flagged.
◆ What a successful import looks like
Config admin shows, e.g. — Imported 17 items from “pt-multirobot” · 3 need input · 6 open Q for Engineering (the pt-multirobot report seeds 17 fields, 39 tools, 3 structures).

What you get back: a map + the open questions

Once a report is present, two cards render:

  • “System architecture” — a diagram (services → datastores → external / integration points) built from the report's components & integrations. needs_input integrations show as warnings.
  • “Open questions for Engineering” — each unknown with a needs_from chip. The “Export for Engineering” button downloads open-questions-<system>.json to hand back to the code owners.
Stage 1 · deployment admin

Admin defines the bounds

Stage 1 lives in Config admin. Here you curate the schema (what can be set) and author rules (what's legal). Rules are previewed against a sample config — no customer's real config is shown on this screen.

The schema (available options)

In the “Available options — schema (DSL)” card:

  • If no schema exists yet, click “Bootstrap from the loaded config” to seed fields/tools/structures from a config — or import a Stage-0 report (above).
  • Each field row: dot.path, a type dropdown (the six field types), options (enum only), a description shown to the customer, and req / adv checkboxes. Add with “+ Add field”.
  • “Offerable tools” — click a tool chip to allow it. If you allow none, all tools are offerable. Give each a description.
  • “Available structures” — choose which of mcp_servers / knowledge_base / transfer_topics the customer may edit.
  • “Draft field” — describe a field in plain English (“a weather provider, enum of openweather / tomorrow.io, required”) and the LLM proposes a field definition.
◆ Destructive vs merge
“Re-bootstrap” and “Clear schema” replace/drop the schema — they don't merge. Re-importing an analysis report, by contrast, merges and preserves your curation.

The rules (what's legal)

Three kinds, authored as data — never baked into code:

KindShapeExample
enumfield must be one of optionsvoice ∈ {alloy, echo, shimmer}
requiresif when then needstool:send_email → field:notification_service_url
conflictsnot both a and bkb_mode:simple ✕ kb_mode:lightrag

Author them three ways: the structured “Author a rule” form, or “Draft rule” (plain English → one structured rule, grounded in your tools & fields), and every rule carries a level — error (blocks the customer) or warn (advisory).

◆ enum rules fold into the schema
On save, an enum rule whose field is a declared schema field is folded into that field's options (and the rule is dropped). The admin's options literally become the customer's dropdown in Stage 2.

Save draft vs Save & publish

Both write a new immutable version. “Save draft” does not move the published pointer; “Save & publish” sets published_version to the latest.

◆ Only the published version is enforced
Stage 2 gates against the published ruleset — not the latest draft. If your new rule “isn't working,” the usual cause is you clicked Save draft, not Save & publish.
Stage 2 · customer / operator

Configure within bounds

Stage 2 lives in Config viewer. A fresh project starts empty. Everything you do here is checked against the admin's published schema + rules — you literally cannot apply a config the rules forbid.

The guided editor

The “Guided edit” card renders widgets from the schema:

  • Agent prompt — the robot's global instructions (a first-class textarea; no SOP required).
  • Tools — clickable chips; only schema-allowed tools are offerable, with the admin's descriptions.
  • Fields — typed widgets: enum → dropdown (an out-of-range value shows … — not allowed), boolean → true/false, number → number input. Markers: * required, ⚑ needs_input, ← needed by a violated rule. A “Show advanced” toggle hides plumbing.
  • Complex structures — row editors for MCP servers, knowledge bases, and transfer topics, each re-evaluated live against the rules.
  • Connector reuse — “+ from connector…” adds an MCP server from the registry as a reference ({connector, authorization:"secret:…"}); “Save as connector” promotes an ad-hoc URL into the registry so SOPs can bind it too.

The Config assistant (chat)

The floating “💬 Config assistant” button opens a persistent chat that remembers the conversation — it's a real assistant, not a one-shot box. Ask “let the agent send verification SMS” or “make the prompt more concise”. It proposes formal edits (enable a tool, set a field, add an MCP server, edit the prompt…). Each proposal is rule-gated: edits that would introduce an error-level violation are shown but marked “the admin's ruleset forbids this — not applied”. Otherwise click “Add to edits” to stage them.

◆ It can't invent capabilities
The assistant may only touch tools/fields the schema declares — unknown atoms are skipped and surfaced, never silently applied. (“Enable X” also works for a schema-allowed tool not yet in the config — it creates the entry, exactly like clicking the chip.)

The commit ladder — the #1 thing to understand

There are four distinct levels. Getting these confused is the most common trip-up, so the UI calls it out explicitly.

ActionWhat it doesPersists?
Apply changesWrites staged edits into the working config (updates JSON + graph). Blocked by error-level violations.Browser only
SavePUT /config/document — a new immutable DB version (draft).DB (not deployed)
Save & publishNew version and moves the published pointer. Disabled if there are errors.DB (deployed)
DownloadRenders the deploy-ready config.json (resolves refs — see §08).Downloads a file
◆ Applied ≠ Saved
Apply changes commits to your in-browser working config; it does not reach the database. Your draft now survives switching tabs (and shows an unsaved chip), but you must click Save or Save & publish to persist it. Discard changes throws the local draft away and reloads the last-saved DB version.

Blocking violations are the guidance

When an edit breaks a rule, the violations panel explains it and offers one-click fixes derived from the rule itself — e.g. clearing notification_service_url while send_email is on shows a blocking error and a “Disable send_email” button. Error-level violations disable Apply changes, Save & publish, and Download until resolved.

Write-back · automatic

Turning the config into the robot's config.json

“Download” calls POST /config/render-robot, which resolves every reference server-side and returns a deploy-ready config.json (downloaded as <display_name>-config.json). Raw credentials never pass through the browser.

What it resolves:

  • Connector refs — an mcp_servers entry with a connector name gets its url (and, if the connector has an auth_secret, a secret: authorization) filled from the registry; the connector key is stripped. Missing/disabled/non-MCP connectors produce a note and the entry is kept as typed.
  • Secret refs — any authorization: "secret:<name>" is Fernet-decrypted and emitted as Bearer <value>. A missing secret leaves the reference in place with a note.
  • Advisory schema notes — if a schema is published, the config is validated against it (required set? enum in range? types right?). These are notes only — write-back never blocks; the Studio already gates on rule errors.
◆ Deployment decision (PolarTie)
Per the PolarTie team, this rendered config.json is the robot's config — it replaces the earlier robot-side config optimizer (a pilot), rather than complementing it. SOPilot does not replace the robot's own knowledge-base MCP servers; it carries the procedures and steering the robot consults over /mcp.

Operations

Reproducible end-to-end script

The whole three-stage cycle, with a restart-survival proof, is scripted:

# 1) write all three stages + verify persistence
python scripts/e2e_config_manager.py \
    --base http://127.0.0.1:8100 --admin-token "$SOPILOT_ADMIN_TOKEN" \
    --tenant pt-e2e --project robot1

# 2) restart the API   (systemctl restart sopilot-api, or redeploy)

# 3) prove nothing was lost — re-fetch only, no writes
python scripts/e2e_config_manager.py --base http://127.0.0.1:8100 \
    --admin-token "$SOPILOT_ADMIN_TOKEN" --tenant pt-e2e --project robot1 --verify-only

Both runs end with ALL CHECKS PASSED. It creates the tenant/project if missing, imports the pt-multirobot report, publishes a schema + rule, publishes a customer config, then re-fetches all three and asserts they match. It never deletes the tenant. A dependency-free report validator lives at scripts/validate_analysis_report.py; the full manual walkthrough is docs/CONFIG_MANAGER_E2E.md.

Deployment settings you'll touch

SettingPurpose
SOPILOT_ADMIN_TOKENDeployment-operator credential (header X-Admin-Token); the admin console login. Required in prod — generate with openssl rand -hex 24; rotate by editing env + restart.
SOPILOT_HOST / SOPILOT_PORTAPI bind (default 127.0.0.1/8100). Studio dev: SOPILOT_UI_PORT (5174), SOPILOT_API_URL.
SOPILOT_MCP_MOUNTtrue mounts the MCP surface at /mcp in-process. Single-tenant — must also set SOPILOT_API_KEY + SOPILOT_PROJECT. SOPILOT_MCP_MODE = tool|supervisor|both.
SOPILOT_SUBSYSTEMSDefault subsystem mode (both|sop|retrieval|advisory).
OPENAI_API_KEYLLM key — server-side only, never sent to the client. The config manager's LLM endpoints use BUILDER_MODEL.
SOPILOT_SECRET_KEYFernet key for tenant connector secrets. Set it before storing any secret, or references won't resolve at write-back.
◆ MCP mount gotcha
SOPILOT_MCP_MOUNT=true alone won't work — it's single-tenant and needs SOPILOT_API_KEY + SOPILOT_PROJECT, and behind a reverse proxy you need proxy_buffering off; proxy_http_version 1.1; for the streaming surface. Full go-live checklist in docs/INTEGRATION.md.

Troubleshooting

SymptomCause / fix
“I changed a config, switched tabs, and it was gone.”You clicked Apply changes but not Save. The draft now survives tab switches and shows an unsaved chip — click Save / Save & publish to persist.
“The assistant said it enabled a tool but nothing changed.”The tool wasn't in the schema allowlist (or, previously, wasn't yet in the config). Allow it in Stage 1, or click its chip. Schema-allowed tools now get created on enable.
“…endpoint not found — restart the backend for /config/…”The running backend predates that route. Redeploy/restart the API — it's not a config error.
“Save & publish / Download is disabled.”There are error-level problems (rule violations or structural errors). Resolve them — the guided editor offers one-click fixes.
“My published rules aren't being enforced.”You clicked Save draft, not Save & publish. Only the published version gates Stage 2.
“A secret came out as the literal secret:….”The secret isn't stored (or SOPILOT_SECRET_KEY changed). Re-enter it via the secrets API; check the write-back notes.
“A new tenant already shows another customer's config.”It doesn't — that's the bundled example. A fresh project starts empty; use Load example deliberately. Real data lives in the DB, untouched.
Cheat sheet

Quick-start checklist

  1. Stage 0 — run the system-analysis skill on the target code → validate the report → Config admin ▸ Import analysis report…
  2. Stage 1 — curate the schema (types, enums, required, descriptions), author rules (enum / requires / conflicts), then Save & publish.
  3. Stage 2 — in Config viewer, build the config with the guided editor + assistant, resolve any blocking violations, then Apply changes → Save & publish.
  4. Deploy — Download the rendered config.json and ship it to the robot; point its mcp_servers at SOPilot's /mcp for SOP guidance.
  5. Verify — run e2e_config_manager.py --verify-only after a restart to confirm all three stages persisted.
◆ Two rules of thumb
(1) Only published versions matter downstream. (2) Apply → Save → Publish → Download are four distinct steps.
