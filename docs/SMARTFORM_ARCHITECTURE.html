PolarTie SmartForm × SOPilot · architecture & findings · for review

Filling long medical forms by voice

SmartForm is a PolarTie robot that helps a person complete long, conditional medical forms — like a 269-field workers’-comp questionnaire — by voice, in any language. This document describes the proposed architecture for running it with SOPilot, and what we measured, so PolarTie can decide what to adopt. It reflects the current, confirmed design — no historical detours.

The bottom line

What SOPilot adds to SmartForm

pt-forms already does most of the job well. SOPilot is therefore an add-on, not a replacement — and there are exactly two reasons to adopt it for SmartForm.

Reason 1 — proven, ship-now

Edit-propagation fix (“reconcile”). Today, when a patient corrects an earlier answer, any field that becomes hidden keeps its now-invalid answer — and it prints on the PDF. SOPilot’s constraint engine recomputes visibility and voids those stale answers. On the real form this closed 61 stale answers → 0, in ~30 ms, as a thin add-on that leaves pt-forms’ engine intact.

Reason 2 — candidate, evaluate

Constraint-graph Studio. Authoring & maintaining a 269-field dependency graph is hard and risky. SOPilot makes it visible, AI-editable, contradiction-checked, and traceable — cheaper and safer to build and maintain, with an audit trail for medical governance. Built and in the SOPilot UI; weigh it against pt-forms’ existing builder.

How it works

Architecture — one principle, four roles

A form is a deterministic, value-gated state machine: fields plus show-if conditions (isYes({Q26}), values[{age}] >= 18). The design follows one rule:

Keep the decision (which question is next) deterministic. Use the language model only for language and judgment — never to decide navigation.

◆ The one thing to remember
constraints.py decides navigation — within a stage and across stages — by evaluating the form’s own conditions. The SOP is passive structure the engine reads (stages give the supervisor a small, relevant context; they don’t navigate). The LLM never decides which field is next; it phrases the question and handles judgment. This is why the mechanisms compose instead of competing.
Build once, offline

Turning a form into a SOP

A one-time pipeline (scripts/form_to_sop.py) ingests a pt-forms fields.json and produces three stored artifacts in SOPilot:

SOP (stages)

Fields grouped into dependency-cohesive stages (269 → 20). Versioned, editable in the Studio.

Playbook blocks

One prompt block per stage (its questions + how to phrase/coerce) + a global flow block. The supervisor’s bounded context.

Map block

A JSON index: each field’s stage, condition, and pt-forms id — the deterministic driver’s lookup table.

◆ Adding a form is data, not code
The engine is generic. Onboarding a new form = run the pipeline on its fields.json — no changes to constraints.py (it already covers the full condition grammar: isYes/isNo/values[…], comparisons, compound and/or/not). You’d touch engine code only for a genuinely new construct.
Per turn, at each Next/Prev

Runtime — one prepared turn

The realtime voice agent calls one endpoint per turn (POST /formflow/prepare). Because the person clicks Next/Prev to advance, this call is off the latency-critical path.

Measured live end-to-end: the deterministic decision (incl. the get-fields read) is ~19 ms; the optional strong-model phrasing is ~1 s, at the tolerant Next/Prev boundary.

The proven win

Edit-propagation — correcting an earlier answer

On “which question is next?” pt-forms and SOPilot are identical (both evaluate the rules). They diverge in one place that matters clinically: when a patient changes an earlier answer so a question they already answered no longer applies.

◆ The defect
“Were you admitted to hospital?” → Yes. “For how long?” → 5 days. The patient corrects the first answer to No. The “how long?” field is now hidden — but its value “5 days” stays in the record and prints on the PDF. pt-forms recomputes visibility forward but does not clear stale answers behind an edit.

The fix — POST /formflow/reconcile: after an edit, recompute visibility with constraints.py and void every answered-but-hidden field (iterating to a fixpoint, so cascades resolve), writing “not applicable” back to pt-forms.

Honest note: this isn’t exclusive technology — pt-forms could add the same reconcile to its own MCP. What the experiment proves is that the gap is real and sized, and that SOPilot’s constraint engine closes it cleanly.

Completeness

Repeating groups

Some sections repeat — one medication, then another; each prior injury. pt-forms models this with a Repeater field whose RepeatFrom marks the group; each instance is stored as <field>[i]. SOPilot handles them across all three layers.

The boundary

Integration with pt-forms

SOPilot and pt-forms meet at exactly two points: once offline (ingest the form) and once per turn / per edit (read answers, write voids). No shared database, no duplicated answer store.

What we measured

Evidence

All on the real 269-question form. Two findings shape the architecture; one is the win.

1 · Navigation must be evaluated, not inferred

If a language model decides the next field (instead of evaluating the conditions), it mis-handles skip-logic. This is why both pt-forms and SOPilot keep gating deterministic.

2 · Robot accuracy — parity, end-to-end

With a real weak voice model in the loop (context-capped), both flows fill the whole 269-field form correctly, because in both the model only relays and the support system decides.

The candidate value — built

Constraint-graph Studio

The rules that drive a 269-field form are the hard part to author and maintain. The Studio (in the SOPilot UI) makes them visible, editable, safe, and observable — three capabilities pt-forms’ builder doesn’t combine:

1 · Visualize

The whole dependency graph from the live rules: 269 fields · 143 conditional · 182 edges · 0 cross-stage · 0 dangling, with hub controllers (one question can gate 30 fields).

2 · AI-edit, checked

Change a rule in plain English → the model proposes a condition → it’s contradiction-checked (dangling refs, self-reference, cycles, always-true/false) → you see a diff → apply only if valid.

3 · Live trace

Set answers and watch the graph light up: answered · to-ask · hidden · stale (a stale field is one reconcile would void) — gating and edit-propagation, visible in real time.

◆ Why this is the maintenance story
Authoring rules as prose for a model to interpret is cheap to type but unvalidatable (silent regressions). The Studio keeps rules explicit and deterministic yet cheap to edit — AI-assisted, contradiction-checked, diffable, with impact analysis and reconcile for the consequences. Cheap and safe — the right trade for medical forms.
◆ Scope — what the Studio does and doesn’t do today
The Studio edits an existing form that was ingested from pt-forms — it loads the graph produced by the pipeline, then lets you visualize, AI-edit, validate and trace it. It does not yet create a form from scratch (add fields, define a new graph) in the UI, and its source is the pt-forms fields.json. So, as built, this is a SmartForm-scoped tool, not a general-purpose constraint editor. The engine underneath (constraints.py) is written generically, so a source-agnostic “generic constraint Studio” (create-from-scratch + import adapters) is a plausible future SOPilot-platform initiative — but that is out of scope for the SmartForm decision.
