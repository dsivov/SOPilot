The use case

What SmartForm is

A person needs to fill a long medical form — a QME “Injured Worker Questionnaire” runs to 271 fields across ~30 sections. SmartForm does it as a conversation: the robot asks one question, the person answers by voice (in any language), and the answer is translated, validated and written into the form on screen.

The form is not a flat list — it's a dependency graph. Whole branches appear or vanish based on earlier answers:

If the person……then SmartForm
says they have no attorneyskips “attorney's name”
says they were not admitted to hospitalskips “how long admitted / what was wrong”
is 4 years oldnever asks “how many children”
wants to add another doctor / lifted object / symptomloops the whole sub‑section again (a “repeater”)
later changes their mind on an earlier answer…must re-open the right branch — this is where it gets hard

Add to that: relative dates (“the same day I got injured”), transliteration of names, an up-front security check, section/info/signature cards, and doing all of it over a voice model with a 32k context window. Those pressures are the five problems below.

The lay of the land

How it works today

The design is deliberate and, importantly, the same shape SOPilot uses: a server-authoritative state machine exposes a minimal, one-field-at-a-time interface to a stateless voice agent. The agent's own prompt says it plainly:

“You are a minimal forms agent. The MCP server handles navigation, validation, skip logic… Your job: ask the question, collect the answer, and send it back.”

◆ The dependency logic, concretely
Each field can carry a FieldCondition — a sandboxed boolean expression like isYes({surgery}) or values[{age}] >= 18 — evaluated server-side (forms_mcp_server.py:474). A field whose condition is false is skipped and stored as “not applicable”, and the agent is simply never handed it. (There's also a second, fuzzy natural-language IF/THEN rule layer — two skip engines to keep in mind.)
Why the five problems exist

The one core insight

All five problems are consequences of a single fact:

A form is a stateful dependency graph that is far too big for a 32k voice model to hold — so the state must live in an engine, and the agent must stay small.

PolarTie already made the right structural move (server-authoritative state + minimal agent). That disposes of the naïve version of each problem. What remains is the hard residual in each — and that residual is exactly where a formal constraint-graph + supervisor (what SOPilot is) has something to add.

1

Navigation

SOPilot leverage: highsolve first

Move to any field by meaning or position, in any language — “fix my age”, “back to my address”, “two back”, “next unanswered”, “question 5”.

Today
forms_navigate(request, current_field_id) → the server matches on question text (_resolve_field_id_by_question :342) and steps over skipped fields.
Hard residual
paraphrase / multilingual matching; “where I said Ryanair” (match by answer content); near-duplicate ambiguity (~20× “hours per day you X”; “doctor's name” in 3 sections + a repeater); repeater-instance jumps (“the 2nd object's weight”); relative moves over a sparse/looping graph + display-number vs internal-id confusion; ~1s latency + voice-friendly one-question disambiguation.
SOPilot fit
a built analog: the intake/switch router (semantic intent→graph node, multilingual, ASR-robust, per-turn) is a better resolver; a semantic field index (question + alt-name + current value, confidence-scored) improves precision + disambiguation.
Verdict ≈
Parity — premise was wrong. On reading the code, forms_navigate already resolves jumps with GPT (_gpt_pick_field, any language, ambiguity handling) — not text-matching. Our semantic router isn’t part of the agreed SOP design and underperformed pt-forms’ GPT navigator in a quick test. No SOP added value here; pt-forms handles navigation well.
2

Question answering

SOPilot leverage: moderate

Turn messy voice/ASR input into the field's validated value.

Today
the LLM agent does it, guided per-field by an Answer format: line + prompt rules — date normalisation (incl. relative & “same day as the injury”), transliteration, option-matching, unknown/not applicable; the server re-asks on validation error; #alert for alert conditions.
Hard residual
robustness under ASR noise; cross-field derivations; alert recognition is fragile in a “minimal” agent; long free-text read-back/confirm.
SOPilot fit
per-turn steering could inject stronger per-field validation + precedent (“how prior callers answered this field”); advisory mode fits the voice latency budget.
Verdict ≈
Parity — measured. We built the strong-supervisor /formflow/interpret step and A/B’d it vs the weak model + pt-forms’ rule-based normalizer over 31 realistic + hard cases (slang, unit conversion, multilingual, relative dates): both 100%. gpt-4o-mini is already good enough; the strong model matches but doesn’t beat it. Not a differentiator.
3·4

State & sync — remember, edit, propagate

SOPilot leverage: highest

Remembering answers, letting the person change their mind, and keeping the dependency graph consistent. These two are really one problem.

Forward skip-logic (“don't ask children if age = 4”) the server already does. The genuinely hard part is backward propagation when an earlier answer changes:

Today
the server stores answers (submissions.data), resumes from a saved-answers block, and supports a requested-changes revision walk. Skip-logic appears to run forward.
Open question
does the server already do backward edit-propagation (invalidate + re-surface), or only forward? This decides how big #3/#4 really is.
SOPilot fit
this is SOPilot. The constraint-graph engine (requires / conflicts / enum, evaluated over state) does forward + backward + conflicts, plus authoring & verification tooling for the dependency graph — a real pain for 271-field forms with two overlapping skip engines.
Verdict ✓
SOLVED — the one proven win. Confirmed in code that pt-forms does not propagate backward (a now-hidden field keeps its stale answer, which prints on the PDF). We built /formflow/reconcile (constraints.py recomputes visibility and voids answered-but-hidden fields to a fixpoint, so cascades resolve). Head-to-head on the real form: Original leaked 61 stale answers → SOPilot 0, at ~30 ms. (Not exclusive tech — pt-forms could add the same reconcile — but the gap is real, sized, and closed.)
5

Realtime voice context — the 32k wall

SOPilot leverage: high

The voice model has a ~32k token window. A 271-field form and a 30–60 minute call don't fit.

The fix
because the server is the source of truth, the voice model's history is disposable: aggressive sliding-window / compaction, periodic session re-init that reloads only guidelines + current field + a compact answers-so-far summary, and a lean, stable system prompt.
SOPilot fit
SOPilot's whole thesis — hold state in the engine, keep the responder context minimal, assemble only what this turn needs — is precisely this mitigation; it could own the per-turn context block + the answers-so-far summary + compaction triggers.
Verdict ≈
Parity — and 32k didn’t even bind. For this form the whole-form catalog is only ~4.7k tokens, so a 32k window never overflows; the naive model’s errors were reasoning, not context. And both systems are already support-authoritative — the weak model only relays and sees one field/instruction — so context stays tiny in each. (a) is solved in both; (b) long-call transcript growth is real but the server-authoritative design (pt-forms and SOP alike) makes history disposable. Not a SOP differentiator.

The direction we chose ★

Proposed solution — a strong supervisor + grouped playbooks

The reframe: the five problems share one cause — the realtime voice model is weak and has a 32k window. So stop engineering around it: move the thinking to a strong text model and hand the realtime model only compact, prepared instructions. That is exactly SOPilot's core pattern — a strong supervisor steering a weak responder per turn.

◆ Built & measured since — an honest update
We built this and A/B’d it. The architecture is sound and shipped, but it did not turn all five problems into SOP wins. On navigation, answer-capture and context pt-forms was already strong, and the measured result is parity. The reframe’s genuine, proven payoff is backward edit-propagation — the reconcile step (61 leaked answers → 0). See measurement, head-to-head, and the reckoning for the numbers. The sections below describe the architecture as built.
◆ The enabler PolarTie already has
In the real app the user clicks Next / Prev to advance — so the realtime model's latency is not on the critical path. That click is a generous window in which a strong supervisor can read the whole situation and return a prepared instruction. It's the SOPilot supervisor window, handed to us for free.

◆ Why this dissolves the five problems
Navigation — the supervisor resolves "go to X" against the current group; jumps just load another stage. Answering — a strong model interprets the answer with the playbook's guidance. State & sync — the supervisor recomputes from the full answer set; constraints.py guarantees consistency. 32k — the form never enters the realtime context; only a compact per-turn instruction does. And crucially, the SOP model is untouched — we reuse it for structure, never bending its probabilistic runtime.
The honest engineering ledger

What we reused, what we added, how they integrate

Almost everything is reuse. The design deliberately keeps PolarTie's working system intact and adds a thin supervisor layer — here's the exact split.

Reused — PolarTie (pt-forms)
  • The form definitions (fields.json: questions, FieldConditions, options, sections) — the input we ingest.
  • The answer store (submissions.data) — the single source of truth.
  • pt-forms' own deterministic form engine + browser UI — unchanged.
  • The realtime voice agent + the Next/Prev turn boundary (our latency window).
  • The pt_ai_agent_mcp supervisor seam — to deliver the prepared instruction.
Reused — SOPilot
  • The SOP model (TaskDefinition, Sop/SopVersion) — stages = groups; structure, versioning, Studio visibility.
  • Prompt blocks (D-7) — the playbooks, flow block & map block; versioned + editable in the Studio.
  • The supervisor pattern — a strong model preparing a compact per-turn instruction.
  • The strong model (builder_model), tenancy/scoping, and block resolution (resolve_published_blocks).
Newly added
  • constraints.py — the canonical server-side constraint engine (value conditions) both forms and config lacked.
  • form_to_sop.py — the offline grouping pipeline (form → grouped SOP + blocks).
  • The stage↔field map block — the deterministic driver's index.
  • /formflow/prepare — the supervisor endpoint (deterministic driver + strong-model prep).
◆ The boundary in one line
pt-forms owns the form definitions, the answers, the browser UI and the realtime voice agent. SOPilot owns the grouped playbooks (structure), the deterministic gating, and the strong per-turn supervisor. They meet exactly twice: once offline (ingest defs → SOP) and once per turn (prepare call). No shared database, no duplicated answer store.
How the SOP deterministic flow works

The flow in detail — three stored artifacts, one engine, one endpoint

Everything the runtime needs is stored as ordinary SOPilot objects (a SOP + prompt blocks), read by a deterministic driver that calls a strong model only to phrase each turn. Here is exactly what each piece is and how they interlock.

1 · What is stored (built once, offline, by scripts/form_to_sop.py)

The form SOP

A TaskDefinition whose 20 stages are the dependency-cohesive question groups — each an agent_action referencing its playbook block. Versioned (Sop/SopVersion), visible & editable in the Studio. Edges are both — the user may jump to any stage, no forced order.

Playbook blocks

One prompt block per stage = its questions + show-if rules + how to coerce answers (dates, names, “don’t know”). Plus one global __flow__ block = the supervisor’s standing instructions. First-class, versioned, reviewable — authors edit the playbook, not code.

The map block

A JSON __map__ block: the stage order, and for every field {name, id, label, cond}. This is the deterministic index — O(1) field→stage, and the id is the pt-forms get-fields id, so live answers bind with no guesswork.

2 · The deterministic engine (constraints.py)

evaluate_condition(cond, answers) is a sandboxed evaluator of the form’s own show-if grammar (isYes/isNo/values[{…}] + comparisons; a missing answer ⇒ false; numeric strings coerced). _visible_unanswered(…) walks the stages in order, skips any field whose condition is false, and returns the first visible, unanswered field — crossing into a later stage (or an earlier one, if the user went back) when the current stage is exhausted. This is the whole “which question is next?” decision — no model.

3 · The runtime loop (POST /formflow/prepare, one call per Next/Prev)

◆ Which part actually navigates? (a common misread)
All navigation — within a stage and across stages — is constraints.py (step c). The stage boundary is not a navigation boundary; the engine crosses it transparently. The map/SOP does no navigating: it’s a passive index (field → stage → playbook) consulted in steps b and d only to load the right playbook for phrasing, plus the ordered field list the engine walks (that order is just the form’s field order — the same data pt-forms has). This is why “SOP is not the navigation engine” and “the flow uses the SOP” are both true: the engine decides; the SOP is the phone book it consults. The SOP’s own transition mechanism (LLM + edges) is off.
◆ Bounded context — with stage-to-stage jumps
The supervisor never sees the whole form — only the playbook of the stage the next question lives in (~550 tokens). Crucially, that window follows the deterministic pointer across stage boundaries: when gating skips to a field in a later group, or the user jumps back to an earlier one, prepare resolves the target stage and loads its playbook. So the context stays ~one stage no matter where in the 20-stage form the answer flow moves.

4 · A concrete turn

◆ Worked example
User just answered Q39 “Did you go to the hospital?” → No. prepare: get-fields says Q39=No; map puts Q39 in History of Treatment; constraints.py finds Q40–Q43 all gated isYes({Q39}) ⇒ hidden, exhausts the stage, and returns the next visible field — Q45 in the next stage. prepare loads History of Treatment (part 2)’s playbook (not the whole form) and the strong model returns one line: “Please describe the treatment you received.” One deterministic hop across a stage boundary; one bounded phrasing call.

Architecture FAQ — a question PolarTie will ask

Three “transition” mechanisms — how they fit together

pt-forms has deterministic field transitions; SOPilot’s SOP has stage transitions steered by an LLM; and SOPilot also has the constraints.py rule engine. They look overlapping. They aren’t — because two different things are being conflated: structure and the transition engine.

MechanismKindDecides “what’s next” byLive in SmartForm?
SOP stage/edge transitions (the ordering mechanism)probabilistic (LLM + predictor)an LLM reading the conversation; edges carry no conditionsNo — this ordering mechanism is off; the stages themselves are still used (context + authoring)
pt-forms field rulesdeterministicevaluating FieldConditionsYes (pt-forms runtime)
SOPilot constraints.pydeterministic (superset)same rules + requires/conflicts/enumYes — the sole transition authority
◆ “So are SOP stages used at all in the form flow?”
Yes — heavily, just not for transitions. Stages do three jobs: (1) grouping (269 fields → 20 groups), (2) bounded context — the supervisor loads only the current stage’s playbook (~550 tokens) to phrase a turn, not the whole form (~4.7k); the stage is that window, and (3) authoring — the unit edited in the Studio. What stages do not do is decide the next step: constraints.py picks the next field (crossing a stage boundary when needed, then loading that stage’s playbook), and the SOP edges are inert. Delete the stages and transitions still work — you’d just lose the bounded context and the authoring structure. So stages are load-bearing for context & authoring, not control flow.
◆ The one-liner for PolarTie
SOP = structure (stages + playbooks). Transitions are pluggable: probabilistic (LLM) for conversations, deterministic (constraints.py, equivalent to pt-forms’ FieldConditions) for forms. SmartForm runs the deterministic engine and keeps the LLM off the transition decision entirely — the SOP edges are inert, constraints.py drives, the model only phrases. That’s why the mechanisms compose instead of competing — and it’s exactly what the A/B forced (LLM-decided transitions ≈ 56%, deterministic = 100%).
For the pt-forms developer — is SOP/playbook right for navigation?

Navigation: which mechanism handles each task

Short answer to the developer’s question: a playbook/SOP is the wrong tool for navigation — it’s an LLM prompt for phrasing one turn, not control flow, and it fits none of the list. Navigation splits across four mechanisms, none of them a playbook:

DET

Deterministic engine — constraints.py + the driver + relative stepping. Most of the list.

RES

Semantic resolver — a GPT/embedding matcher for “by meaning”. pt-forms already has this (_gpt_pick_field).

HIST / DERIVE

HIST: an answer-history/trace store. DERIVE: the interpret step (parse + compute) or a form formula.

◆ Two things to tell him
(1) This isn’t SOPilot replacing your navigation. We measured navigation at parity — pt-forms already does the deterministic parts and the GPT “by content” resolver well. The table just says which tool each task needs, and it’s DET/RES/HIST/DERIVE — never a playbook. (2) Where the SOP world adds something next to 1.2: when the user goes back and changes an earlier answer, the hard part isn’t the jump — it’s the propagation afterward (downstream answers now hidden). That’s reconcile (our one measured win, 61 stale → 0). So 1.2 + reconcile compose: DET does the jump, constraints.py cleans up the consequences.

Why deterministic gating — and an honest correction

Why the “next question” decision must not be model-inferred

◆ Correction — read this first
An earlier draft framed this as “SOP vs what pt-forms does today.” That was wrong, and reading pt-forms’ source proved it: pt-forms already decides the next field deterministically server-side (_compute_next_field → _should_skip_field → _evaluate_field_condition, plus a deterministic .md-rule layer), and its agent only relays the server’s question. So this experiment is not a win over pt-forms — both pt-forms and our SOP flow gate deterministically. What it actually shows is the shared principle underneath both designs: if you let a model infer skip-logic instead of evaluating it, it gets ~1-in-3 gating decisions wrong. pt-forms and SOPilot independently arrived at the same answer — don’t.

The decision under test: “which question is next?” — ask the right one, skip the ones the form’s rules hide. Ground truth is the form’s own show-if rules (isYes/isNo/values[…]), evaluated exactly.

Inference (the anti-pattern)

A model infers the next field from the whole form + answers — what happens if navigation is left to the realtime model with no deterministic backing. Two tiers: weak = gpt-4o-mini, strong = gpt-4o. Neither production system does this — it’s the strawman that quantifies the risk.

Evaluation (both systems)

The next field is evaluated from the FieldConditions. pt-forms does it in _compute_next_field; our SOP flow does it in constraints.py. Same principle, correct by construction.

◆ What this shows (and doesn’t)
Does show: the decision of which field is next must be evaluated, not inferred — inference costs ~1-in-3 skip errors, ~0.8–0.9 s, and ~4.7k tokens every turn; evaluation is exact at ~0 ms and 0 tokens. Does NOT show: a SOP advantage over pt-forms — pt-forms already evaluates deterministically. The strong model still runs each turn in our design, but only to phrase the pre-decided question (~1.07 s, ~550 tokens), off the correctness path. Reproduce: scripts/smartform_bench/ (README + harness + mock).

“Let the LLM navigate within a stage” — tested

The original idea was a hybrid: constraints handle stage-to-stage; an LLM handles in-stage navigation (from the playbook). We had only tested the strawman (LLM over the whole form). ◆ Can a better playbook + the STRONG supervisor close the gap? (we searched)
We took one self-contained stage (30 conditional fields) and swept playbook formats with the real supervisor model (gpt-4o). A clean playbook ties deterministic: terse / rules / inline / few-shot all hit 100%. Two lessons: (1) format matters non-monotonically — terse & clear wins; chain-of-thought actively hurts (76% even on gpt-4o; the weak model too). More words ≠ better. (2) For gating, the playbook isn’t under-informative — the show-if conditions are the complete information; the strong model uses even the terse form to reach 100%. But across all stages it’s ~90% overall / ~100% conditional (residual = ordering / premature-“done”, some of them unsafe skips), and it’s a probabilistic tie on a sample, not exact-by-construction, at ~0.8 s + tokens/turn. So the supervisor can navigate, but there’s no accuracy reason to spend it there. Where richer playbooks genuinely pay off is the non-navigation work — coercion, judgment, the fuzzy .md rules, phrasing — which is where the strong supervisor actually beats the weak realtime model. Lab: scripts/smartform_bench/playbook_lab.py.
◆ The real prize is authoring cost — here’s the safe way to win it
The strongest argument for the hybrid isn’t runtime — it’s that authoring 269 conditions is hard, while “stages + let the LLM handle in-stage” is light. True. But two facts reframe it: (1) all deps are intra-stage, so “LLM in-stage” means the LLM owns all 182 gates (≈88%, weak); (2) the failure modes differ — under-authored + deterministic = over-ask (a maybe-irrelevant question; safe), whereas under-authored + LLM = wrong-skip (a missed required question; unsafe for medical intake). So get the authoring win in the authoring layer, not the runtime: author only the safety-critical gates (the rest are asked in order), and make full authoring cheap with the constraint-graph Studio (visualize + AI-assisted edit + contradiction-check). Make authoring easy and keep execution deterministic — don’t move navigation to the LLM.
Robot accuracy — end-to-end, with a real weak voice model

Does the robot fill the whole form correctly?

We put an actual weak model — gpt-4o-mini, context capped at 32k (the realtime voice model’s budget) — in the loop as the voice agent, and ran the full 269-question form to completion under both setups. Ground truth is the form’s own show-if rules: did the robot ask all-and-only the visible fields, honor every skip, and reach the end?

◆ The one thing that decides this
Who chooses the next question? If the weak voice model chooses (the naive approach), it misreads skip-logic ~1 turn in 3 (see previous section). If the support system chooses and the weak model just relays — which is how both 🅐 Original pt-forms (its server) and 🅑 SOPilot (its supervisor) work — the weak model can’t steer the form wrong. That’s why both complete accurately.

Robot accuracy — capturing the answer

Turning what the patient says into the value to store

◆ Two new terms, in plain words
Answer-capture = converting what the patient says (messy, spoken, any language) into the exact value to store in the field. Coercion rules = the rules for that conversion — spoken numbers → digits (“forty-five” → 45), any date phrasing → YYYY-MM-DD, yes/no wording → Yes/No, a described choice → exactly one listed option, and “don’t know” / a refusal → unknown.

This is the robot’s core language job. We built it as a SOPilot step (POST /formflow/interpret, the strong supervisor applying the SOP flow block’s coercion rules) and A/B’d it against how pt-forms does it today.

The real head-to-head — Original vs SOPilot

Where the two flows genuinely differ: a corrected answer that hides a question

On “which question is next?” the two systems are identical (both evaluate the rules deterministically). The one place they diverge — and it’s a real medical-data-integrity issue — is what happens when a patient corrects an earlier answer so a question they already answered no longer applies.

◆ What “reconcile” means (new term)
Reconcile = a quick cleanup pass that re-checks the form’s show-if rules against the current answers and removes any answer that no longer applies. When a correction hides a question that was already answered, reconcile marks that stale answer “not applicable” so it cannot reach the PDF. It is a single server call (POST /formflow/reconcile) run after an edit — think of it as “tidy up the answers after a change.”
 🅐  Original pt-forms🅑  SOPilot (SOP + reconcile)
What it is The current production flow: the pt-forms MCP server + Laravel backend + the voice agent. The SOP flow (this project) plus one new step: POST /formflow/reconcile.
Skip logic Deterministic, server-side (_compute_next_field). Deterministic (constraints.py) — identical behaviour.
When a patient corrects an earlier answer The now-hidden question keeps its old answer — nothing clears it (_get_next_empty_field_id skips already-valued fields; the PDF drops only blank / “not applicable”, never re-checking conditions). Reconcile recomputes visibility and voids every answered-but-hidden field (to a fixpoint, so cascades are handled), writing “not applicable” back to pt-forms.
◆ The defect, in one example
“Were you admitted to hospital?” → Yes. “For how long?” → 5 days. The patient then corrects the first answer to No. The “how long?” question is now hidden — but in 🅐 Original pt-forms the value “5 days” stays in the record and prints on the PDF. In 🅑 SOPilot, reconcile voids it.

Completeness — repeating groups

Repeaters: “list each medication…”, done right

Some form sections repeat — one medication, then another; each prior injury; each dependent. pt-forms models this with a Repeater field whose RepeatFrom marks the group start; every instance is stored as <field>[i]. This was the one construct the spike didn’t handle — now it does, across all three layers.

LayerWhat it does for repeaters
Pipeline (form_to_sop.py)Detects the Repeater + its members (from RepeatFrom up to the repeater, mirroring pt-forms) and writes repeat_group/members into the map block; keeps the whole group in one stage.
prepareServes each visible unanswered member at the current instance, then the “add another?” control; per-instance gating (a member’s show-if is evaluated on that instance’s values). Yes → next instance, No → past the group.
reconcileInstance-aware: voids <member>[i] hidden at that instance, and voids all instances + the now-moot “add another?” answer when the whole group is hidden — so a removed or hidden repeating item can’t leak stale answers into the PDF.
◆ Role & how to use
Role: completeness — forms with repeating sections work end-to-end, and the proven reconcile win extends to repeating data (the highest-risk place for stale answers). How to use: author it in pt-forms as a Repeater field with RepeatFrom — the pipeline picks it up automatically, no engine code (adding a form, repeaters and all, stays a data operation). Instances are addressed <name>[i] in the answer snapshot. Covered by 13 tests against a synthetic repeater fixture — no pt-forms sample form uses repeaters, so we built one to validate all three layers.
A candidate added value — not yet proven

Config-driven authoring & governance

Distinct from the proven value (reconcile). This one is about who can change the form’s behaviour, and how it’s governed — an authoring/ops benefit, not a runtime-accuracy one (accuracy is parity, as measured).

◆ One honest correction to the premise
pt-forms’ state machine is not code-based at the rule level — its FieldConditions are already config, authored in pt-forms’ own visual condition builder. Both systems are “generic engine (code) + per-form rules (config)”. So SOP doesn’t move a code machine to config; it moves a wider slice of behaviour into versioned, Studio-editable config.

◆ Adding another form = data, not code
The engine is generic. To onboard a new form you run the ingest pipeline (form_to_sop.py) on its fields.json — no changes to constraints.py. It already covers the full FieldCondition grammar (isYes/isNo/values[…], comparisons, and compound AND/OR/NOT — the real form uses 40 AND conditions). You’d touch engine code only for something new: an unseen operator, pt-forms’ fuzzy .md rule layer, repeaters, or a new field type. (Same is true of pt-forms’ own generic engine.)
◆ Honest status of this value
Real for medical governance — non-engineers editing grouping, instructions & coercion in one versioned, auditable place instead of touching server code + agent_prompt.md + .md files. But it’s a product/ops benefit to be validated against pt-forms’ existing builder, not a measured accuracy win. Candidate, not proven.
